# Phase 4 — Distributed Cache with Consistent Hashing

## The Core Problem

Current architecture:

```
                 CacheInterface
                       |
                       |
                  RedisCache
                       |
                   Redis Server
```

All cache keys:

```
suggestion:iph
suggestion:iphone
suggestion:sam
suggestion:laptop
```

go to a single Redis instance.

Works today.

But imagine:

```
100 million users
1 billion prefixes
TBs of cache data
```

One Redis server becomes a bottleneck:

```
                  Redis
                 /  |  \
                /   |   \
             CPU  RAM  Network
                 LIMIT
```

We need horizontal scaling.

---

# The Naive Approach

Most people think:

```
Redis A
Redis B
Redis C
```

and:

```python
node = hash(key) % 3
```

Example:

```
hash("iph") % 3 = Redis B
hash("sam") % 3 = Redis A
hash("lap") % 3 = Redis C
```

Looks fine.

---

# The Catastrophic Problem

Suppose we add a new cache server.

Before:

```
N = 3

hash(key) % 3
```

Distribution:

```
iph → B
sam → A
lap → C
usb → A
```

Now add:

```
Redis D

N = 4
```

Now:

```
hash(key) % 4
```

Everything changes:

```
iph → D
sam → C
lap → A
usb → B
```

Almost every key moves.

Result:

```
Old caches useless
       |
       v
Massive cache misses
       |
       v
PostgreSQL gets slammed
       |
       v
Potential outage
```

This is called a **cache avalanche during rebalance**.

---

# The Solution: Consistent Hashing

Instead of:

```
hash(key) % number_of_servers
```

we create a **hash ring**.

Imagine a circle:

```
                    0
                    |
            Redis A |
                  \ |
                   \|
270 ----------------+---------------- 90
                   /|
                  / |
            Redis C |
                    |
                   Redis B
                   180
```

Every server gets a position on the ring.

---

# Placing a Key

Example:

```
Key:
suggestion:iphone
```

Compute:

```
hash("suggestion:iphone")
```

Suppose it lands here:

```
             Redis A


                 *
                 |
                 |
Key ------------>
                 |
                 |
             Redis B
```

We move clockwise until we find the first server.

That server owns the key.

---

# Adding a New Node

Before:

```
A -------- B -------- C
```

Add:

```
D
```

After:

```
A ---- D ---- B ---- C
```

Only keys between:

```
A and D
```

move.

Everything else stays.

---

# This is the entire reason consistent hashing exists

Instead of:

```
Adding 1 server
        |
        v
80-90% key movement
```

we get:

```
Adding 1 server
        |
        v
~1/N keys move
```

This is the main viva point.

---

# Another Problem: Uneven Distribution

Imagine three nodes:

```
Ring:

A                 B
|
|
|
|
|
C
```

The ranges are:

```
A owns 50%
B owns 10%
C owns 40%
```

Bad.

---

# Solution: Virtual Nodes

Each physical Redis gets multiple positions.

Instead of:

```
Redis A
```

we create:

```
Redis A-1
Redis A-2
Redis A-3
...
```

Example:

```
              A1


      C3               B1


 A2                       B2


      C1              A3


             B3
```

Now ownership is much more balanced.

# Milestone 4.3 — DistributedCache Implementation

Create:

```
distributed_cache.py
```

It implements:

```
CacheInterface
```

Internally:

```
get(key):

    node = hash_ring.get_node(key)

    return node.redis.get(key)
```

Same for:

```
set()
delete()
```
