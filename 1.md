# PHASE 1 — PostgreSQL Typeahead Baseline

## Philosophy

We are intentionally building a "slow" system.

Not because it is bad.

Because we need a baseline.

The final story should be:

```
We measured the bottleneck.
Then we optimized it.
```

Not:

```
We added Redis because everyone adds Redis.
```

---

# Phase 1 Goal

At the end of this phase:

A user should be able to make:

```
GET /suggest?q=iph
```

and receive:

```json
{
  "prefix": "iph",
  "suggestions": [
    {
      "query": "iphone 15 pro max case",
      "historical_count": 523
    },
    {
      "query": "iphone charger",
      "historical_count": 481
    }
  ]
}
```

The entire request path:

```
HTTP Request
      |
      v
FastAPI Router
      |
      v
Service Layer
      |
      v
Repository Layer
      |
      v
PostgreSQL
      |
      v
Prefix Index
```

Nothing else.

# Why This Architecture?

Even though this is a simple API, we do not write:

```python
@app.get("/suggest")
def suggest():
    sql()
```

because later phases will introduce:

```
suggest()
  |
  |-- cache lookup
  |
  |-- ranking logic
  |
  |-- database fallback
```

So we establish boundaries now.

# Request Lifecycle

## Step 1 — Client sends request

Example:

```
GET /suggest?q=iph
```

---

## Step 2 — API validation

Validate:

* q exists
* trim whitespace
* convert to lowercase
* reject extremely long prefixes

Examples:

Good:

```
iph
iPhone
  IPH
```

becomes:

```
iph
```

Bad:

```
""
```

returns:

```json
400 Bad Request
```

---

# Step 3 — Service Layer

Current logic:

```
SuggestionService
        |
        |
        v
Repository
```

No business logic yet.

Just orchestration.

---

# Step 4 — Repository Query

The actual SQL:

```sql
SELECT
    query,
    historical_count
FROM queries
WHERE query LIKE :prefix || '%'
ORDER BY historical_count DESC
LIMIT 10;
```

Important:

Use:

```
LIKE
```

not:

```
ILIKE
```

because we normalized data to lowercase.

This allows PostgreSQL to use:

```
idx_query_prefix
```
