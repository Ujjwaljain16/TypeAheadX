# Phase 5 — Search Submission, Write Buffering & Batch Processing

This phase is arguably the second most important phase after Phase 4 because it completes the **write path** of the system.

Until now, we optimized:

```
User typing
     |
     v
READ PATH
     |
     v
Distributed Cache
     |
     v
PostgreSQL
```

But the assignment also requires:

```
User submits search
        |
        v
Update query popularity
        |
        v
Avoid writing to DB every request
```

That means we need a **write optimization architecture**.

---

# The Naive Design (We Will NOT Do This)

Every search:

```
POST /search
      |
      v
UPDATE queries
SET count = count + 1
WHERE query='iphone'
```

Imagine:

```
100,000 users search iphone
```

You execute:

```
100,000 UPDATE statements
```

Problems:

* Excessive disk writes
* Lock contention
* High database CPU
* Poor scalability

---

# The Correct Architecture

## Write Buffer + Batch Flusher

```
                   POST /search
                         |
                         v
                  Search API
                         |
                         v
                 Write Buffer (Memory)
                         |
                         |
                 +-------+------+
                 |              |
          Size Threshold    Time Threshold
                 |              |
                 +-------+------+
                         |
                         v
                 Batch Aggregator
                         |
                         v
                 PostgreSQL UPSERT
```

---

# Core Design Philosophy

Very important:

The user should **never wait for PostgreSQL**.

When a user searches:

```
POST /search
```

Response:

```json
{
  "message": "Searched"
}
```

immediately.

The database update happens asynchronously.

This is called **eventual consistency**.

## Buffer Data Structure

Do not store:

```
iphone
iphone
iphone
iphone
samsung
iphone
```

That defeats batching.

Use aggregation.

Example:

```python
{
 "iphone": 5,
 "samsung": 1,
 "laptop": 3
}
```

# Milestone 5.3 — Flush Strategy

Two triggers.

## Size-based flushing

Example:

```
BATCH_SIZE = 1000
```

When:

```
1000 unique updates collected
```

Flush.

---

## Time-based flushing

Example:

```
FLUSH_INTERVAL = 5 seconds
```

Even if traffic is low:

```
User searches "rare query"

waits forever ❌
```

Instead:

```
5 seconds pass
        |
        v
flush
```

---

# Milestone 5.4 — Batch Database Writer

Use PostgreSQL UPSERT.

Something like:

```sql
INSERT INTO search_queries(query, historical_count)
VALUES (...)
ON CONFLICT(query)
DO UPDATE
SET historical_count =
search_queries.historical_count +
EXCLUDED.historical_count;
```

This is extremely important.

Why?

Because it handles:

```
Existing query:
iphone + 100

New query:
new ai gadget + 1
```

with the same statement.

# Milestone 5.5 — Background Worker

FastAPI startup:

```
App starts
      |
      v
Start batch worker thread/task
```

Loop:

```
sleep(5 sec)
       |
       v
Check buffer
       |
       v
Flush to PostgreSQL
```

Shutdown:

```
Application stopping
        |
        v
Flush remaining events
```

No lost writes during graceful shutdown.

Why accept this?

Because:

```

```

are not financial transactions.

```

```

# Cache Interaction (Very Important)

After batch flush:

```
Database counts changed
```

Our cache may be stale.

For Phase 5 we have two choices.

## Option A — TTL only

Let the existing:

```
5 minute cache expiry
```

handle it.

Simple.

---

## Option B — Selective invalidation

During flush:

```
iphone updated
       |
delete:
suggestion:i
suggestion:ip
suggestion:iph
...
```

Complex.

---

My recommendation:

**Choose Option A.**

Reason:

* We already designed TTL.
* Trending will modify ranking later.
* Prefix invalidation is surprisingly expensive.

Document this tradeoff.
