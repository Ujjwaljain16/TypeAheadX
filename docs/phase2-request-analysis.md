# Phase 2: Prefix Request Analysis

## Objective
To mathematically and empirically observe the API read patterns generated by real user interaction via the frontend application. 

This analysis monitors the HTTP calls generated when an end-user types naturally, factoring in our 250ms debounce and AbortController implementation.

## Scenario: Single User Typing "iphone"

**Typing session input:**  
`i` → `ip` → `iph` → `ipho` → `iphon` → `iphone`

### Observed Network Requests
Because of the **250ms debounce window**, we do *not* generate a request for every single keystroke. Instead, the frontend intelligently waits for natural typing pauses.

For a typical fast typist, the actual network calls generated might look like:
1. `GET /suggest?q=ip` (pause)
2. `GET /suggest?q=iphon` (pause)
3. `GET /suggest?q=iphone` (completion)

**Potential prefixes:** 6 (`i`, `ip`, `iph`, `ipho`, `iphon`, `iphone`)  
**Actual network calls:** Typically 1-3 depending on typing speed.

### AbortController Behavior
During this session, `useSuggestions` correctly aborts in-flight requests when newer ones trigger. If Request 1 (`ip`) is still waiting for the database when Request 2 (`iphon`) fires, Request 1 is immediately canceled, saving client resources and preventing stale renders.

## The Real Cache Justification

While debounce successfully mitigates the "every keystroke is a query" problem for a single user, it does *not* solve the macro-level scale problem.

**Across a large user population, popular prefixes remain exceptionally "hot."**

Examples of heavily repeated prefixes across thousands of users:
- `iph`
- `iphone`
- `samsung`
- `air`

Even with perfect frontend debouncing, these hot prefixes will cause identical, repeated database reads from thousands of different concurrent sessions. At scale, these non-deterministic text searches (`LIKE 'prefix%'`) will cause significant CPU and memory I/O strain on PostgreSQL, regardless of indexes.

**Verdict:** Our observation explicitly justifies introducing a **Distributed Cache Layer** in Phase 3. 

We now have the mature data to prove that caching isn't just to stop a single user from spamming the database—it's because population-level data shows that many users repeatedly search the exact same popular prefixes. Intercepting these hot prefixes via a blazing-fast key-value store (Redis) will drastically reduce relational database load while ensuring sub-millisecond suggestions.
