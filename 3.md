# Why Do We Need Caching?

The important thing is:

**Not because one user is typing quickly.**

Debouncing solved that.

The actual problem appears at scale.

Imagine:

```
100,000 users
```

Many of them search:

```
iphone
samsung
airpods
laptop
usb
```

The requests look like:

```
User A:
GET /suggest?q=iph

User B:
GET /suggest?q=iph

User C:
GET /suggest?q=iph
```

Today:

```
Every request
        |
        v
PostgreSQL
        |
        v
Same SELECT query
        |
        v
Same results
```

This is unnecessary work.

---

# Phase 3 Goal

Transform:

## Before

```
FastAPI
   |
   v
PostgreSQL
```

into:

## After

```
                 Cache Hit
                    |
                    v
Client
  |
FastAPI
  |
Suggestion Service
  |
  +----------------+
  |                |
  |                |
Cache            PostgreSQL
  |                |
  |                |
Return         Cache miss
results            |
                   v
              Query DB
                   |
              Store result
                   |
              Return
```

This is the classic:

# Cache-Aside Pattern

---

# Why Cache-Aside?

Alternatives:

## Write Through

```
App
 |
Cache
 |
Database
```

Good for writes.

But we currently have:

```
GET /suggest
```

which is a read-heavy endpoint.

---

## Cache-Aside

Flow:

### First request

```
GET /suggest?q=iph

Cache:
MISS

↓


Postgres:

SELECT * 
WHERE query LIKE 'iph%'
ORDER BY count DESC
LIMIT 10

↓

Result

↓

Store:
cache["iph"] = results
```

---

### Second request

```
GET /suggest?q=iph

Cache:
HIT

↓

Return directly
```

# Milestone 3.1 — Introduce Cache Abstraction

The biggest mistake would be:

```python
import redis

def get_suggestions():
    redis.get()
```

inside your service.

Why?

Because Phase 4 is coming.

Phase 4 requires:

```
Multiple cache nodes
+
Consistent hashing
```

If Redis is tightly coupled now, we rewrite everything later.

---

## Introduce an interface

Architecture:

```
SuggestionService
        |
        v
CacheInterface
        |
        |
        +---- InMemoryCache
        |
        +---- RedisCache (Phase 3)
        |
        +---- DistributedCache (Phase 4)
```

---

Repository structure evolves:

```
 |

 |

```

# Milestone 3.3 — Cache Key Design

Very important.

Bad:

```
iphone
```

Why?

What does it mean?

A query?
A cache entry?
A ranking?

---

Use namespaced keys.

Example:

```
suggestion:iph
suggestion:iphone
suggestion:samsung
```

---

Future proof.

Later:

```
trending:daily
user:123:history
```

---

# Milestone 3.4 — Cache Value Design

Store:

```json
[
  {
    "query": "iphone 15",
    "historical_count": 50000
  }
]
```

Redis stores bytes.

Therefore:

```
Python object
        |
        v
JSON serialization
        |
        v
Redis
```

---

# Milestone 3.5 — TTL Strategy

Very important.

Do not keep forever.

Why?

Future phases:

```
POST /search
```

will update counts.

The cache must eventually refresh.

---

For Phase 3:

```
TTL = 5 minutes
```

Reason:

Good balance:

```
Freshness
vs
Database load
```

# Important Design Decision

Do we implement consistent hashing now?

## No.

Absolutely not.

Because Phase 3 is:

```
Single logical cache
```

---

Phase 4 is:

```
                Hash Ring
                    |
          +---------+----------+
          |         |          |
       Redis A   Redis B    Redis C
```

The code we write now should allow this.
